## 1. 背景与目标

### 1.1 业务背景

G117 红旗项目中,零跑为红旗代工生产出口车辆,资金流路径为 `1000 公司 → 红旗国内公司`。为防范回款风险,红旗对部分客户引入**保函(Letter of Guarantee, LOG)**机制:客户向银行申请开立保函,银行以信用担保客户付款义务;金融专员在系统录入保函并审核,PO 提交时按"换算订单额度比例"冻结保函可用金额,在质检通过、SAP 清账、失效等节点分阶段解冻/转应收/释放。

### 1.2 设计目标

- **统一金额池**:保函可用/占用/应收三态金额强一致,杜绝超扣、超转。
- **资金闭环**:5 种资金变动(冻结、解冻、转应收、释放应收、保函失效)全程留痕。
- **优先级消费**:系统按"失效日期升序 → 可用金额降序 → 随机"自动选取最优保函,降低人为干预。
- **多对多拆分**:一个保函可对多订单,一订单可拆多保函(按金额比例拆分)。
- **审核/作废可控**:三角色(金融专员/金融管理/红旗商务)严格分工,状态机不可越权跳变。
- **失效自动化**:保函到期日系统凌晨定时任务自动失效,无需人工干预。

### 1.3 范围

本设计覆盖:
- 保函主数据(CRUD、审核、提交、作废[仅草稿/驳回]、提前失效[仅审核通过])
- 保函交易明细(冻结/解冻/转应收/释放应收/保函失效 5 种类型流水)
- 保函选择策略(PO 提交时按优先级选保函)
- 保函失效定时任务(凌晨自动,仅对审核通过的保函生效)
- 与 PO 订单的资金联动接口(本服务暴露,PO 模块消费)

不在本设计范围(由其他模块负责):
- 客户信息维护(参见 `客户信息管理` 设计)
- PO/SO 订单管理
- 应付清单管理
- SAP 对账(本服务仅记录释放应收事件,SAP 同步由 SAP 集成模块负责)

## 2. 业务概述

### 2.1 核心概念

| 术语 | 含义 |
|------|------|
| 保函(Letter of Guarantee, LOG) | 银行开立的书面信用担保凭证,担保客户对零跑的付款义务 |
| 保函编号 | 银行端唯一编号,系统中全局唯一 |
| 换算订单额度比例 | `保函订单金额 = 保函金额 × 比例`;可低于 100%(部分担保)或等于 100%(全额担保) |
| 可用订单金额 | `保函金额 × 比例 - 已占用订单金额 - 已转应收订单金额 + 已释放应收订单金额` |
| 占用订单金额 | PO 提交且未质检通过时冻结的金额 |
| 应收订单金额 | 质检通过后已转入应收的金额 |
| 客户资金校验类型 | 客户维度配置,值为 1=无校验 / 2=保函;为 2 时 PO 提交必须绑定保函 |
| 失效日期 | 保函到期日,系统凌晨任务按此字段判定自动失效 |

### 2.2 关键业务规则

1. **不同客户不同保函**:保函必须挂接具体客户,跨客户不允许共用。
2. **多对多拆分**:一个保函可同时被多个 PO 部分占用;一个 PO 可由多个保函分摊(各按比例)。禁止单一保函金额被超额占用。
3. **金额守恒**:任何时点 `可用 + 占用 + 应收 - 释放应收 = 保函金额 × 比例`。
4. **状态机严格**:
   - 审核状态:
     - `草稿(10) → 已提交(20) → 审核通过(30)`,或 `已提交(20) → 驳回(40) → 草稿(10)`。
     - **作废** 适用于:**草稿(10)** 与 **驳回(40)**(均为未启用的保函);`已提交(20)` 审核中与 `审核通过(30)` 均**不可作废**。
     - 审核通过(30) 的终止**只能**通过"提前失效"操作(修改 `lg_status`,不影响 `approval_status`)。
     - 已通过的保函不可再驳回(只能保持或提前失效)。
   - 保函状态(`lg_status`):`10(未生效) → 20(有效) → 30(失效)`(草稿/提交/驳回/作废阶段为 10,审核通过置 20,到期或手动失效置 30)。
     - **失效** 主要针对**已审核通过**的保函,可由金融专员"提前失效"手动触发(如银行撤销、银行保函到期提前),也可由系统凌晨任务按 `expiry_date` 自动触发。
     - 作废(approval_status=50) 与 失效(lg_status=30) **正交独立**:
       - **作废** 是**流程层面终结**,仅适用于**未启用**(草稿/驳回)的保函,作废后不可再被任何业务使用。
       - **失效** 是**资金层面失效**,仅适用于**审核通过**的保函,失效后:不可被新增占用,但既有占用/应收可继续走完流程(冻结/解冻/转应收/释放应收 仍可执行)。
     - 草稿(10)/驳回(40) 作废时,`lg_status` 保持 `10`(从未启用,无需"有效"标记);审核通过(30) **不走作废**,只走提前失效(`lg_status: 10→20→30`,即审核通过先置 20,失效再置 30)。
5. **保函优先级**(PO 提交选保函时):
   1. 失效日期升序(快到期的优先用完)
   2. 可用订单金额降序(优先用足额的大保函)
   3. 随机(打破平局)
6. **保函失效自动任务**:每日凌晨扫描 `expiry_date < today AND lg_status=有效` 的保函,标记为失效,并将剩余可用金额释放(写一条 `保函失效` 类型流水)。
7. **角色权限**:
   - 金融专员:录入(草稿)、提交、作废
   - 金融管理:审核(通过/驳回)
   - 红旗商务:仅查看

## 3. 业务流程

### 3.1 保函主数据维护流程

```

   │                                │                        │
   │──① 录入保函(草稿) ────────────>│                        │
   │   客户/类型/银行/金额/比例/      │                        │
   │   生效日/失效日                  │                        │
   │                                │                        │
   │──② 提交(已提交) ─────────────>│                        │
   │                                │                        │
   │                                │──③ 审核 ──>            │
   │                                │   3a 通过(保函有效)     │
   │                                │   3b 驳回(回到草稿)     │
   │                                │                        │
   │<──④ 审核结果 ───────────────────│                        │
   │                                │                        │
   │──⑤ 作废(草稿/驳回) ───────────>│                        │
   │   5a 草稿作废:无任何校验          │                        │
   │   5b 驳回作废:无任何校验          │                        │
   │   5c 审核通过:**不可作废**       │                        │
   │                                │                        │
   │──⑥ 提前失效(已审核通过) ───────>│                        │
   │   主要用于银行撤销/到期提前等场景  │                        │
   │   联动 lg_status: 1→2           │                        │
   │   占用/应收保留,可继续走完流程    │                        │
   │                                │                        │
   │                                │                  ⑦ 凌晨任务
   │                                │                  扫描 expiry_date<today
   │                                │                  标记失效+写失效流水

### 3.2 PO 提交选保函流程(由 PO 模块调用本服务)

```
PO 模块                              保函服务
  │                                    │
  │──① 校验客户资金校验类型=2 ────────>│
  │                                    │
  │──② 查询可用保函(按优先级) ────────>│
  │                                    │
  │<── 返回可用保函列表(可用金额倒序) ──│
  │                                    │
  │  业务侧决定分摊比例(可拆多保函)      │
  │                                    │
  │──③ 冻结金额(传保函ID+金额+PO号) ──>│
  │   校验:每张保函可用>=冻结金额       │
  │   写:占用+=,可用-=,写冻结流水       │
  │<── 成功/失败 ─────────────────────│
```

### 3.3 资金变动 5 种类型

| 类型 | 触发场景 | 资金变动 | 流水方向 |
|------|---------|---------|---------|
| 10 冻结 | PO 提交 | 占用 +, 可用 - | PO → 保函 |
| 20 解冻 | PO 驳回 | 占用 -, 可用 + | 保函 → PO |
| 30 转应收 | 质检通过 | 应收 +, 占用 - | 保函 → 应收 |
| 40 释放应收 | SAP 清账 | 应收 - (保函不补回,核销完毕) | 应收 → SAP |
| 50 保函失效 | 凌晨任务/提前失效(人)/审核通过(30)终止时联动 | lg_status: 20→30;可用=0(若有);占用/应收保留,继续走完流程(后续转应收/释放应收 仍允许) | 内部调整 |

### 3.4 PO 提交-保函校验与冻结契约

> G117 红旗项目 PO 订单提交时,资金校验与冻结分两步:
> - **步骤 3(资金校验)**:PO 模块前置读取客户资金校验类型,=2 时调用保函服务 `/app/basic/exportVehicleLetterGuarantee/validate`(走 §8.5 AppController 内部 HTTP,非 Feign)校验,失败立即终止提交;
> - **步骤 4(冻结保函)**:保函服务 `/app/basic/exportVehicleLetterGuarantee/batchFreeze` 一次性冻结多张保函,服务端按优先级排序 + 逐步拆冻,任一失败整体回滚。

#### 3.4.1 整体流程

```
PO 模块                                  保函服务
  │                                          │
  │── ① 读客户主数据,资金校验类型 ────────>│   (Customer 服务 / 本地缓存)
  │   若=1 无,跳过;若=2 保函,继续          │
  │                                          │
  │── ② /validate(cId, orderType,           │
  │              total, orderCreateTime) ──>│
  │                                          │
  │   校验 a~f 规则(见 §3.4.2)              │
  │<── passed=true/false + 可用列表 ─────────│
  │                                          │
  │   若 passed=false → 报错终止              │
  │   业务侧确认 → 进入步骤 4                 │
  │                                          │
  │── ③ /batchFreeze(cId, orderId,          │
  │                 orderNo, total,          │
  │                 orderCreateTime) ──────>│
  │                                          │
  │   服务端:优先级排序 + 逐步拆冻(§3.4.3)    │
  │   校验可用金额、写主表 + N 条流水         │
  │   @Transactional,任一失败整体回滚         │
  │<── success + frozenList(逐张) ───────────│
```

#### 3.4.2 步骤 3 资金校验规则(对应 `/validate`)

| 项 | 校验内容 | 说明 |
|---|---------|------|
| 前置 | 客户资金校验类型 = 2(保函) | 在 PO 模块前置读客户主数据,=1 直接跳过;**前置校验失败不调保函服务** |
| a | 保函【订单类型】= 订单【订单类型】 | `lg.order_type` 与 PO 的 `orderType` 完全相等;若保函 `order_type=NULL`(通用),是否参与校验?**待确认**(建议通用 = 全匹配,需业务确认) |
| b | 保函状态 = 有效 | `lg_status = 20` |
| c | 审核状态 = 审核通过 | `approval_status = 30` |
| d | 生效日期 ≤ 订单创建时间 | `effective_date <= orderCreateTime` |
| e | 失效日期 ≥ 订单创建时间 + X 天 | `expiry_date >= orderCreateTime + coverDays`;**X 为系统参数 `letterGuarantee.coverDays`,默认 100 天**,Nacos 配置可调 |
| f | SUM(满足以上条件的所有保函的【可用订单金额】) ≥ 订单总金额 | 累加 `available_amount` 与 PO `totalAmount` 比较;**严格 ≥**(若 <,校验失败) |

**校验失败返回**:`passed=false` + `failCode` + `failMessage`,常见 `failCode`:

| failCode | failMessage(中) | 触发条件 |
|----------|----------------|---------|
| `LG_NO_AVAILABLE` | 提交失败,资金校验未通过,请联系商务 | a~e 任一不满足导致可用保函为 0 |
| `LG_INSUFFICIENT_FUNDS` | 提交失败,资金校验未通过,请联系商务 | 可用保函总额 < 订单总金额(f 项失败) |
| `LG_ORDER_TYPE_MISMATCH` | 订单类型与可用保函不匹配 | a 项无任何保函通过 |

> **业务约定**(来自需求原文):即使校验通过,PO 模块也不应在 UI 上提前选保函,让用户提交时由系统自动拆冻;若用户希望手动选保函,见 §8.1 `/listAvailable` HTTP 端点(展示用,不影响冻结)。

#### 3.4.3 步骤 4 拆冻算法(对应 `/batchFreeze`)

**入参**:PO 提交时调用 `/batchFreeze`,传订单 ID/号/总金额/创建时间;**不传保函列表**(由保函服务端自行查询、排序、拆冻)。

**算法**(在保函服务 CmdExe 内执行,**单一 `@Transactional` 事务**):

1. **查询可用保函**:复用 §3.4.2 的 a~e 规则,得到候选集 `availableSet`;
2. **优先级排序**(三键稳定排序):
   - 主键:失效日期 **升序**(近的优先);
   - 次键:可用订单金额 **降序**(多的优先);
   - 末键:`RAND()` **随机**(分页不可控问题,见 §14 #7);
3. **逐步拆冻**(累计冻结金额累加器 `frozenSum=0`,目标 `targetAmount=订单总金额`):
   - 遍历排序后候选集;
   - 取下一张保函,`take = min(当前保函可用金额, targetAmount - frozenSum)`;
   - 校验:`take > 0`(若 =0,跳过此保函);
   - **对该保函执行单张冻结**:
     - 校验 `当前保函可用金额 >= take`(防并发,另加 Redis 分布式锁 `key=lg:{lgId}`,见 §11.1);
     - 主表:`available_amount -= take`;`occupied_amount += take`;`update_time = NOW`;
     - 流水表:新增 1 条 `transaction_type=10(冻结)`,按 §3.4.5 字段表填值;
   - `frozenSum += take`;
   - 若 `frozenSum == targetAmount`,跳出循环;
4. **结果判断**:
   - 若 `frozenSum == targetAmount`:返回 `success=true` + `frozenList`;
   - 若 `frozenSum < targetAmount`(**理论不应发生**,因 §3.4.2 f 已校验):抛 `LG_INSUFFICIENT_FUNDS`,事务整体回滚;
5. **回滚语义**:`@Transactional(rollbackFor=Exception.class)` + 主表/流水表同事务;**任一保函冻结失败 → 全部回滚**(已成功的也撤销),保持资金一致性。

#### 3.4.4 内部 HTTP 端点契约(AppController)

> **本节契约由 §8.5 `ExportVehicleLetterGuaranteeAppController` 落地**(非 Feign),路径前缀 `/app/basic/exportVehicleLetterGuarantee/`,Java 代码与 DTO 包名见 §8.5.1~8.5.3。本节仅描述字段语义与业务规则。

##### `/validate` (POST `/app/basic/exportVehicleLetterGuarantee/validate`)

**请求** `ExportVehicleLetterGuaranteeValidateReq`:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| customerId | String(36) | ✓ | 客户 ID |
| orderType | String(16) | ✓ | 订单类型(CBU/SKD/CKD) |
| totalAmount | BigDecimal | ✓ | 订单总金额 |
| orderCreateTime | LocalDateTime | ✓ | 订单创建时间(用于 d/e 校验) |

**响应** `ExportVehicleLetterGuaranteeValidateResp`:

| 字段 | 类型 | 说明 |
|------|------|------|
| passed | Boolean | true=通过,可进入步骤 4;false=终止提交 |
| totalAvailable | BigDecimal | 满足 a~e 的保函可用金额合计(供 PO 端展示) |
| availableList | List<AvailableItem> | 按 §3.4.3 优先级排序的保函明细(`lgId` / `lgCode` / `availableAmount` / `expiryDate` / `lgType`) |
| failCode | String | 失败时返回(`LG_NO_AVAILABLE` / `LG_INSUFFICIENT_FUNDS` / `LG_ORDER_TYPE_MISMATCH`);通过时为空 |
| failMessage | String(i18n key) | 失败时返回的国际化文案 key(如 `dict.letterGuarantee.validate.fail.insufficient`) |

##### `/batchFreeze` (POST `/app/basic/exportVehicleLetterGuarantee/batchFreeze`)

**请求** `ExportVehicleLetterGuaranteeBatchFreezeReq`:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| customerId | String(36) | ✓ | 客户 ID |
| orderId | String(36) | ✓ | PO 单 ID(用于 Redis 分布式锁 / 操作日志,无持久化字段;关联关系通过 `po_no` 体现) |
| orderNo | String(30) | ✓ | PO 单号(写 `po_no`) |
| totalAmount | BigDecimal | ✓ | 订单总金额 |
| orderCreateTime | LocalDateTime | ✓ | 订单创建时间(冗余记录,便于审计追溯) |
| creator | Long | ✓ | 操作人 ID(写入流水,映射到基类 creator 字段) |
| creatorName | String | ✓ | 操作人名称(写入流水,映射到基类 creator_name 字段) |

**响应** `ExportVehicleLetterGuaranteeBatchFreezeResp`:

| 字段 | 类型 | 说明 |
|------|------|------|
| success | Boolean | true=全部成功;false=整体失败(已回滚) |
| frozenList | List<FrozenItem> | 逐张冻结明细(`lgRecordCode` 流水号 / `lgId` / `lgCode` / `lgType` / `freezeAmount` / `beforeAvailable` / `afterAvailable` / `beforeOccupied` / `afterOccupied`) |
| failCode | String | 失败时返回(如 `LG_BATCH_FREEZE_FAILED` / `LG_INSUFFICIENT_FUNDS`) |
| failMessage | String(i18n key) | 国际化文案 key |

> **设计要点**:
> - PO 端**必须先调 `/validate` 通过再调 `/batchFreeze`**,否则 batchFreeze 自身会再次校验 a~f(避免跨调用状态漂移);
> - `batchFreeze` 内部对每张保函加 Redis 分布式锁 `lg:{lgId}`(§11.1),保证并发安全;
> - 整体事务 `@Transactional(rollbackFor=Exception.class)`,**回滚时已冻结的金额自动恢复**(`available_amount` / `occupied_amount` 回到冻结前值;已写入的 `export_vehicle_letter_guarantee_record` 行同事务回滚清除)。

#### 3.4.5 主表/流水表 字段更新规则

**保函主表**(`export_vehicle_letter_guarantee`,其他字段不变):

| 字段 | 更新说明 |
|------|---------|
| `available_amount` | = 原 `available_amount` - 本次冻结金额 |
| `occupied_amount` | = 原 `occupied_amount` + 本次冻结金额 |
| `update_time` | = NOW |

#### 3.4.7 示例(200 万 PO 单拆冻)

**输入数据**:

```
PO 单 101: 总金额 200万,创建日期 2026-04-15
资金校验类型 = 2(保函)
coverDays = 100 → 要求失效日期 ≥ 2026-04-15 + 100d = 2026-07-24

保函候选:
  保函1: 有效期 2026-03-01 ~ 2026-06-30,可用 20,占用 50,应收 30
  保函2: 有效期 2026-04-20 ~ 2026-08-19,可用 120,占用 0,应收 0
  保函3: 有效期 2026-05-01 ~ 2026-08-31,可用 100,占用 0,应收 0
  保函4: 有效期 2026-05-01 ~ 2026-08-31,可用 150,占用 0,应收 0
```

**步骤 3 /validate**:

```
a. 订单类型=CBU 假设全部一致,均通过
b/c. lg_status=20, approval_status=30,均通过
d. effective_date <= 2026-04-15,均通过
e. expiry_date >= 2026-07-24:
   保函1 失效 2026-06-30 < 2026-07-24 → 排除
   保函2 失效 2026-08-19 ✓
   保函3 失效 2026-08-31 ✓
   保函4 失效 2026-08-31 ✓
f. SUM(可用) = 120 + 100 + 150 = 370 万 ≥ 200 万 → 通过
```

**步骤 4 /batchFreeze 拆冻**:

```
排序(失效升序 → 金额降序 → 随机):
  保函2 (2026-08-19, 120)   ← 最早
  保函4 (2026-08-31, 150)   ← 同日,金额最大
  保函3 (2026-08-31, 100)   ← 兜底

逐步拆冻:
  第 1 轮: target=200, available(保函2)=120, take=min(120, 200-0)=120
          冻结保函2 120万,frozenSum=120
  第 2 轮: target=200, available(保函4)=150, take=min(150, 200-120)=80
          冻结保函4 80万,frozenSum=200  → 达标,跳出
  第 3 轮: 不进入

最终:保函2 冻结 120万 + 保函4 冻结 80万 = 200万(等于 PO 总金额)
```

**主表更新**:

| 保函 | available_amount | occupied_amount | update_time |
|------|------------------|-----------------|-------------|
| 保函2 | 120 - 120 = 0 | 0 + 120 = 120 | NOW |
| 保函4 | 150 - 80 = 70 | 0 + 80 = 80 | NOW |
| 保函3 | 不变(100) | 不变(0) | — |
| 保函1 | 不变(被排除) | — | — |

**流水表新增 2 条**:

|-------|-------|------|--------|--------|--------------|-------------|------------|-----------|------------|-----------|
| `BK20260415143000001` | 保函2 | 10 冻结 | 120.00 | `PO单 101提交,资金冻结` | 120.00 | 0.00 | 0.00 | 120.00 | NULL | NULL |

## 4. 状态机

### 4.1 审核状态(approval_status)

```
              ┌───────── 作废(50) ←──────────┐
              │                              │
   草稿(10) ──提交──> 已提交(20) ──审核通过──> 审核通过(30)
     │   ↑             │                       │
     │   │             └─────驳回──> 驳回(40) ──┘
     │   │                  │
     │   └────── (回到草稿) ─┘
     │
     ├────── 作废(50) ─────> 作废(50)   ← 草稿(10) 可作废
     │
     │                   (驳回(40) 也可作废)
     │                   ┌────── 作废(50) ────> 作废(50)
     │                   │
     └───────────────────┘
     
   审核通过(30) ──> 不可作废(只走"提前失效",见 §4.2)
```

**允许的转换**:

| 起始状态 | 目标状态 | 操作 | 校验 |
|---------|---------|------|------|
| 草稿(10) | 已提交(20) | submit | 必填字段完整性 |
| 草稿(10) | 作废(50) | cancel | 无校验(未启用) |
| 已提交(20) | 审核通过(30) | approve (true) | - |
| 已提交(20) | 驳回(40) | approve (false) | - |
| 驳回(40) | 草稿(10) | 系统回退(审核驳回触发) | - |
| 驳回(40) | 作废(50) | cancel | 无校验(未启用) |
| 审核通过(30) | ~~作废(50)~~ | ~~cancel~~ | **禁止(本设计不允许)** |
| 审核通过(30) | (lg_status: 20→30) | expireEarly | 仅 lg_status 变化;**不要求**金额清零(剩余占用/应收可继续走完流程) |
| 作废(50) | - | - | 终态 |

**状态含义**:
- `10 草稿`:仅金融专员可见,未生效
- `20 已提交`:待金融管理审核,**此状态不可作废**(审核中)
- `30 审核通过`:可被 PO 选用,`lg_status=20(有效)`(审核通过时由 10 置 20);**此状态不可作废**,终止需走"提前失效"
- `40 驳回`:回到草稿,金融专员可修改后重新提交;也可直接作废
- `50 作废`:终止态,不再被任何业务使用

> **不可越权**:`已提交(20)` 不可作废(在审);`作废(50)` 不可被驳回(终态);`审核通过(30)` 不可直接回到草稿(必须经驳回);`审核通过(30)` 不可作废(终止须走"提前失效")。作废仅适用于 `草稿(10)` 与 `驳回(40)` 两个未启用状态。

### 4.2 保函状态(lg_status)

```
   10(未生效) ──审核通过──> 20(有效) ── 提前失效(人)/凌晨任务(系统) ──> 30(失效)
   30(失效) ── 终态 ──────────────────────────────────────────────────────────> -
```

- `10 未生效`:草稿(10)/已提交(20)/驳回(40)/作废(50) 状态下保函未启用;**不参与**任何业务资金操作,仅作流程记录。
- `20 有效`:与 `approval_status=30` 联动出现;只有审核通过后才会被置为 20,方可被 PO 选保函(`listAvailableForCustomer` 仅返回 lg_status=20 的记录)。
- `30 失效`:仅 `approval_status=30` 可触发;`lg_status=30` 后:
  - 不再参与 PO 选保函(`listAvailableForCustomer` 过滤掉)
  - 已有的占用/应收可继续走完流程(冻结/解冻/转应收/释放应收 仍可执行)
  - 不可被新 PO 占用

**与作废的关系(approval_status vs lg_status)**:
- **作废**(approval_status=50) = 流程层面终结,仅适用于**未启用**的保函(草稿/驳回);作废后**不可**再执行任何资金操作。
- **失效**(lg_status=30) = 资金层面失效,仅适用于**已审核通过**的保函;失效后**不可**新增占用,但**可以**继续处理存量占用/应收。
- 草稿(10)/驳回(40) 作废时,`lg_status` 保持 `10`(从未启用,无需"有效"标记)。
- 审核通过(30) **不走作废**,终止只能走提前失效(`lg_status: 20→30`,`approval_status` 仍为 30)。
- 提前失效/凌晨任务仅修改 `lg_status`,**不修改** `approval_status`。
- **完整生命周期**:`10(草稿创建) → 10(提交审核) → 10(审核通过 → 置 20 有效) → 20(到期/手动失效 → 置 30 失效) → 30(终态)`。

### 6.2.1 枚举与 `@DictEnumType` 规范(对齐 `app-ais-maintain`)

> 即使保函字典走 `common_dict` / `common_dict_value` 数据库表(见 §7.3),代码侧**仍需**在 client 层定义枚举,用于:
> 1. **状态流转硬约束**:Service/Gateway 内 `if (status.equals(ApprovalStatusEnum.APPROVED.getCode()))`,避免魔法值;
> 2. **请求/响应字段校验**:Req 字段用 `@EnumValue(enumClass = XxxEnum.class, required = true)` 校验入参;
> 3. **前端自动翻译**:Resp 字段标注 `@DictEnumType(type = XxxEnum.class)`,平台序列化器自动把 code 翻译为 message(class-based 优于 prefix 字符串,IDE 重构友好)。

**枚举基类**:必须实现平台 `com.leapmotor.paltform.ais.common.model.enums.IBaseEnum<T>`。

**`@DictEnumType` 注解路径**:`com.leapmotor.platform.ais.common.web.serializer.DictEnumType`(位于 `web.serializer` 包,与 Jackson 序列化器协同,按枚举类自动翻译 code → i18n message)。

**示例 — 审核状态枚举**:

```java
package com.leapmotor.export.vehicle.letterGuarantee.enums;

import com.leapmotor.paltform.ais.common.model.enums.IBaseEnum;

/**
 * 保函审核状态(对应字段 approval_status,字典 letter_guarantee_approval_status)
 */
public enum ApprovalStatusEnum implements IBaseEnum<String> {
    DRAFT     ("10", "草稿"),
    SUBMITTED ("20", "已提交"),
    APPROVED  ("30", "审核通过"),
    REJECTED  ("40", "驳回"),
    CANCELLED ("50", "作废");

    private final String code;
    private final String message;

    ApprovalStatusEnum(String code, String message) {
        this.code = code;
        this.message = message;
    }

    @Override public String getCode()    { return code; }
    @Override public String getMessage() { return message; }

    public static ApprovalStatusEnum of(String code) {
        for (ApprovalStatusEnum e : values()) if (e.code.equals(code)) return e;
        return null;
    }
}
```

**`LgStatusEnum` 注意**:`10(未生效)` 不入枚举(数据库字段默认值);枚举仅含 `EFFECTIVE("20")` 与 `INVALID("30")`,业务侧遇到 10 走 fallback 文案 `dict.letter_guarantee_lg_status.10=未生效`。

```java
@AllArgsConstructor
@Component
@Transactional(rollbackFor = Exception.class)
public class ExportVehicleLetterGuaranteeCmdExe {

    private ExportVehicleLetterGuaranteeGateway letterGuaranteeGateway;
    private ExportVehicleLetterGuaranteeRecordGateway recordGateway;

    public String addOrUpdate(ExportVehicleLetterGuaranteeDo do) {
        // 业务校验:金额、比例、生效/失效日期顺序等
        validateOnWrite(do);
        // 新增时初始化金额池
        if (do.getId() == null) {
            do.setAvailableAmount(do.getTotalAmount().multiply(do.getConversionRatio()));
            do.setOccupiedAmount(BigDecimal.ZERO);
            do.setReceivableAmount(BigDecimal.ZERO);
            do.setApprovalStatus(APPROVAL_STATUS_DRAFT);
            // lg_status 保持 10:草稿/提交/驳回/作废 时保函未生效,不标"有效"
            // 审核通过时(Gateway.approve approved=true)再置为 '20' 有效
        }
        return do.getId() == null
            ? letterGuaranteeGateway.addExportVehicleLetterGuarantee(do)
            : letterGuaranteeGateway.updateExportVehicleLetterGuarantee(do);
    }

    public boolean submit(String id, Long creator, String creatorName) {
        // 校验:仅草稿可提交、字段完整性
        return letterGuaranteeGateway.submit(id, creator, creatorName);
    }

    public boolean approve(String id, boolean approved, String remark,
                           String approverId, String approverName) {
        return letterGuaranteeGateway.approve(id, approved, remark, approverId, approverName);
    }

    public boolean cancel(String id, Long creator, String creatorName, String remark) {
        // 校验:仅 草稿(10) / 驳回(40) 可作废,均无校验(未启用的保函)
        // 审核通过(30) / 已提交(20) 不可作废
        return letterGuaranteeGateway.cancel(id, creator, creatorName, remark);
    }

    public boolean expireEarly(String id, Long creator, String creatorName, String reason) {
        // 校验:仅 审核通过(30) + 有效(20) 可提前失效
        // 联动:lg_status: 20→30;若有可用金额则置 0;占用/应收保留(继续走完)
        // 不修改 approval_status
        boolean ok = letterGuaranteeGateway.expireEarly(id, creator, creatorName, reason);
        if (ok) {
            // 写一条"保函失效"流水(类型 50)
            recordGateway.addExpireRecordForEarly(id, creator, creatorName, reason);
        }
        return ok;
    }

    public boolean freeze(String lgId, BigDecimal amount,
                          String orderId, String orderNo,
                          String creator, String creatorName) {
        boolean ok = letterGuaranteeGateway.freeze(lgId, amount, orderId, orderNo,
                                                     creator, creatorName);
        if (ok) {
            // 同步写流水
            recordGateway.addFreezeRecord(lgId, amount, orderId, orderNo,
                                                   creator, creatorName);
        }
        return ok;
    }

    // unfreeze / transferToReceivable / releaseReceivable 类似结构

## 7. 数据库设计

### 7.0 基础字段规范(平台通用)

所有业务表统一遵循以下基础字段结构(参照平台建表模板):

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `id` | VARCHAR(36) | 是 | - | 主键,UUID |
| `creator` | BIGINT | 是 | - | 创建者ID(用户ID) |
| `creator_name` | VARCHAR(100) | 是 | - | 创建人名称 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `modifier` | BIGINT | 否 | NULL | 修改者ID |
| `modifier_name` | VARCHAR(100) | 否 | NULL | 修改人名称 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 修改时间 |
| `delete_status` | SMALLINT UNSIGNED | 是 | 0 | 删除状态(0=正常,1=已删除),逻辑删除 |
| `status` | SMALLINT UNSIGNED | 是 | 1 | 状态(1:启用,0:停用) |
| `status_desc` | VARCHAR(256) | 否 | NULL | 状态变更描述 |
| `owner_user_id` | BIGINT UNSIGNED | 是 | 0 | 归属用户ID,数据权限归属到用户时使用 |
| `owner_org_id` | BIGINT UNSIGNED | 是 | 0 | 归属门店ID(组织ID),数据权限归属到本组织及下级时使用 |

**关键约定**:
- 主键统一 VARCHAR(36) UUID,**不用**自增 INT
- 业务实体 ID(customer_id / lg_id / order_id)统一 VARCHAR(36)
- 用户/操作者 ID(creator / modifier / submitter_id / approver_id)统一 BIGINT
- 归属类 ID(`owner_user_id` / `owner_org_id`)统一 `BIGINT UNSIGNED`,默认 0 表示"无归属"
- 逻辑删除:`delete_status` 由 MyBatis-Plus `@TableLogic` 拦截,SQL `WHERE delete_status = 0` 自动追加
- 状态分离:`status`(启用/停用)、`approval_status`/`lg_status`(业务流状态)、`delete_status`(逻辑删除)三者独立,不混用
- 乐观锁**不再**用 `version` 字段(模板未要求),改用 Redis 分布式锁防并发
- 业务字段(如 `remark` / `approve_remark`)按需保留

**保函模块对 owner 字段的使用**:
- `owner_user_id`:录入该保函的金融专员用户ID(可与 `creator` 一致),用于"我录入的"数据权限过滤
- `owner_org_id`:录入人所属组织(门店/部门)ID,用于"本组织及下级"数据权限过滤
- 若保函无明确归属(如系统级保函、字典类),保持默认 0
- 0 值的语义:**平台级共享**,所有用户可见;非 0 值:仅归属用户/本组织及下级可见

**对 LpBaseEntity/LpBaseModel 的影响**:
- 平台 `LpBaseEntity/Model` 当前提供 `createdBy/createdTime/updatedBy/updatedTime/status/remark` 字段,与新模板不一致
- 保函模块建议:**新建** `LpBaseEntityV2` 或在 `LpBaseEntity` 上扩展以下字段并保留老字段以兼容:
  - 新增 `creator/creatorName/createTime/modifier/modifierName/updateTime/deleteStatus/status/statusDesc/ownerUserId/ownerOrgId`
  - `createdBy/createdTime` 等老字段保留(标 `@Deprecated`),后续迁移
- 实施时需与平台组对齐,选择**新建**或**升级**路径

### 7.3 字典说明

保函管理所有枚举字段均通过**平台字典双表 `common_dict` + `common_dict_value` + i18n properties** 三轨维护:
- **平台字典类型表 `common_dict`**:字典类型注册(主键 BIGINT 自增,`dict_type` 唯一)。由 `sql/letter-guarantee-dict.sql` 导入,前端下拉框/后端翻译均读取此表与 `common_dict_value`。
- **平台字典项表 `common_dict_value`**:字典项明细(主键 BIGINT 自增,`dict_type` 冗余,与 `common_dict.dict_type` 一致,便于查询过滤;唯一索引 `idx_dict_type_value(dict_type, dict_value, delete_status)`)。同一 `dict_type` 多行,`dict_value` 存业务侧取值(`varchar(32)`),`dict_label` 存显示名(`varchar(64)`),`sort` 排序(升序)。
- **i18n 文案**:同步到 `properties/common_zh_CN.properties` 与 `properties/common_en_US.properties`,key 格式 `dict.<dict_type>.<dict_value>`,便于直接通过 `MessageSource` 翻译。

**双表关联方式**:`common_dict_value.dict_type = common_dict.dict_type`(冗余字段,不建外键;查询字典项 `WHERE dict_type=?` 即可)。

| 字典类型 (`dict_type`) | 字段 | 取值 (`dict_value`) | 含义 |
|------|------|---------|------|
| `letter_guarantee_approval_status` | `approval_status` | `10` 草稿 / `20` 已提交 / `30` 审核通过 / `40` 驳回 / `50` 作废 | 审核流转 |
| `letter_guarantee_lg_status` | `lg_status` | `10` 未生效 / `20` 有效 / `30` 失效 | 保函业务有效性(仅审核通过置 20,到期/手动置 30) |
| `letter_guarantee_record_type` | `transaction_type` | `10` 冻结 / `20` 解冻 / `30` 转应收 / `40` 释放应收 / `50` 保函失效 | 资金变动流水类型 |
| `letter_guarantee_lg_type` | `lg_type` | `PREPAYMENT` 预付款(G117 红旗项目仅启用预付款) | 保函类型 |
| `letter_guarantee_order_type` | `order_type` | `CBU` / `SKD` / `CKD`(NOT NULL,新增时必填无默认值) | 订单类型 |

**`lg_status` 的 10(未生效)处理**:
- 数据库字段 `lg_status` 默认 `10`(主表 `export_vehicle_letter_guarantee.lg_status` NOT NULL DEFAULT '10',见 §7.1);
- 字典表 `common_dict_value` **仍包含** `10` 项(由 `letter_guarantee_lg_status` 字典维护),`10` 对应文案"未生效";
- 前端下拉框展示"未生效"项,后端翻译时遇到 10 走 i18n 文案 `dict.letter_guarantee_lg_status.10=未生效`。
- `LgStatusEnum` Java 枚举**仅含** `20(有效)` 与 `30(失效)` 两个业务值,`10(未生效)` 由 `ApprovalStatusEnum` 反向推导(草稿/已提交/驳回/作废均对应未生效)。

**字典导入**:执行 `sql/letter-guarantee-dict.sql` 入库;新增字典类型需先注册到 `common_dict`,再插入 `common_dict_value` 项;同时更新 SQL + properties 两份文件,保持同步。

### 8.5 内部 HTTP 接口(`/app/basic/exportVehicleLetterGuarantee`)— PO 提交核心链路

> G117 红旗项目 PO 提交-保函链路(`/validate` + `/batchFreeze`)走 **AppController 内部 HTTP**,**不走 Feign**。原因:
> 1. **业务关键路径**:校验与冻结是资金链路核心动作,Feign 降级(`LG_SERVICE_UNAVAILABLE`)会导致 PO 端误判"系统繁忙"放行,引发资金敞口;
> 2. **事务一致性**:`/batchFreeze` 跨多张保函同事务回滚,要求调用方拿到明确 HTTP 状态码(200/500)而非 Feign 包装的 `AjaxResult`;
> 3. **运维可观测**:走 HTTP 走链路追踪/超时配置/Grafana 看板更直接,Feign 包装层会丢失原始状态码。
>
> **调用方式**:由 PO 模块在本服务集群内**直接 HTTP 调用**(`RestTemplate` / `WebClient`),URL 见下表。**不在 Nacos 上注册为独立服务**,依赖同集群 HTTP 直连。

| 方法 | 路径 | 说明 | 调用方 | 权限码 |
|------|------|------|--------|--------|
| POST | `/app/basic/exportVehicleLetterGuarantee/validate` | **资金校验**(只读):见 §3.4.2,返回 `passed` + 可用保函列表 | PO 模块(步骤 3) | `app:basic:exportVehicleLetterGuarantee:validate` |
| POST | `/app/basic/exportVehicleLetterGuarantee/batchFreeze` | **批量冻结**(写):见 §3.4.3,服务端按优先级排序 + 逐步拆冻,任一失败整体回滚 | PO 模块(步骤 4) | `app:basic:exportVehicleLetterGuarantee:batchFreeze` |

#### 8.5.4 PO 端调用示例(`RestTemplate` 直连)

```java
// PO 模块(本服务集群内)调用保函服务 - 直接 HTTP,不走 Feign
private static final String LG_BASE = "http://app-ais-export-vehicle/app/basic/exportVehicleLetterGuarantee";

// 步骤 3 资金校验
ExportVehicleLetterGuaranteeValidateResp v = restTemplate.postForObject(
    LG_BASE + "/validate", validateReq, ExportVehicleLetterGuaranteeValidateResp.class);
if (!Boolean.TRUE.equals(v.getPassed())) {
    // 业务失败:弹"请联系商务"
    throw new BizException(v.getFailCode(), v.getFailMessage());
}

// 步骤 4 批量冻结
try {
    ExportVehicleLetterGuaranteeBatchFreezeResp f = restTemplate.postForObject(
        LG_BASE + "/batchFreeze", freezeReq, ExportVehicleLetterGuaranteeBatchFreezeResp.class);
    if (!Boolean.TRUE.equals(f.getSuccess())) {
        // 业务失败:可用金额不足等
        throw new BizException(f.getFailCode(), f.getFailMessage());
    }
    // 成功:f.getFrozenList() 是逐张冻结明细,写 PO 侧业务日志
} catch (HttpStatusCodeException e) {
    // HTTP 5xx/4xx:系统失败,允许 PO 端重试(最大 3 次)
    log.error("保函批量冻结 HTTP 异常, status={}, body={}", e.getStatusCode(), e.getResponseBodyAsString());
    throw new BizException("LG_BATCH_FREEZE_FAILED", "dict.letterGuarantee.batchFreeze.fail.retryable");
}

#### 8.5.5 错误码 / 异常处理语义

| failCode | 触发条件 | PO 端处理 |
|----------|---------|----------|
| `LG_INSUFFICIENT_FUNDS` | 可用保函总额 < 订单总金额 | 业务失败,弹"请联系商务",**终止提交** |
| `LG_NO_AVAILABLE` | a~e 任一不满足导致可用保函为 0 | 业务失败,弹"请联系商务",**终止提交** |
| `LG_ORDER_TYPE_MISMATCH` | 订单类型与可用保函不匹配 | 业务失败,弹"请联系商务",**终止提交** |
| `HTTP 5xx` / `HTTP 408` | 保函服务不可达 / 超时 | 系统失败,弹"系统繁忙,请稍后重试",**允许重试**(最大 3 次) |
| `LG_BATCH_FREEZE_FAILED` | 批量冻结事务回滚 | 系统失败,弹"系统繁忙,请稍后重试",**允许重试**(最大 3 次) |

## 10. 异常处理

### 10.1 业务异常

**统一使用平台 `BizException`**(`com.leapmotor.paltform.ais.common.model.exception.BizException`),**不**自建 `LetterGuaranteeException`。平台 `GlobalExceptionHandler` 已统一捕获 `BizException`,返回国际化错误消息。

```java
// 典型用法 (Service / GatewayImpl / CmdExe)
throw new BizException("保函已生效,不可作废");

// 带格式化参数
throw new BizException("可用订单金额不足,需 {0},实际 {1}", needAmount, actualAmount);
```

常见异常消息与触发条件:

| 异常消息 | 触发条件 |
|---------|---------|
| `保函不存在` | getById/update/delete 找不到记录 |
| `保函已作废,不可操作` | 对已作废保函执行任何资金操作 |
| `保函未审核通过,不可冻结` | approval_status ≠ 30 时调用 freeze |
| `保函已失效(到期),不可冻结` | lg_status=30 时调用 freeze |
| `可用订单金额不足,需 X,实际 Y` | 冻结/解冻时金额校验失败 |
| `保函在审核中,不可作废` | cancel 时 approval_status=20 |
| `保函已审核通过,不可作废,终止请走"提前失效"` | cancel 时 approval_status=30 |
| `保函已作废,不可重复作废` | cancel 时 approval_status=50 |
| `保函未审核通过,不可提前失效` | expireEarly 时 approval_status ≠ 30 |
| `保函已失效,无需重复失效` | expireEarly 时 lg_status=30 |
| `已作废保函不可提前失效` | expireEarly 时 approval_status=50 |
| `无效的审核状态转换: X → Y` | submit/approve/cancel 状态机越权 |
| `生效日期必须早于失效日期` | 字段顺序校验失败 |
| `换算订单额度比例必须在 (0,1]` | 比例越界 |

### 10.2 错误日志

所有异常必须 `log.error("保函操作失败, op={}, id={}, amount={}", op, id, amount, e)`,便于追踪资金流水;校验失败信息用 `log.warn` 即可,避免错误日志噪音。

### 10.3 输入校验

Controller 入参使用 `@Validated` + Bean Validation(`@NotBlank`、`@NotNull`、`@DecimalMin`、`@DecimalMax`、`@Schema(requiredMode=REQUIRED)`、`@EnumValue`)做边界校验,枚举字段用 `@EnumValue(enumClass = XxxEnum.class, required = true)`(参考 `app-ais-maintain` 现有用法);校验失败由平台 `GlobalExceptionHandler` 返回 400 + 友好错误消息。

## 11. 风险与约束

### 11.1 资金一致性

- **乐观锁**:**不再**用 `version` 字段(平台建表模板已不要求)。改用 **Redis 分布式锁**做并发控制:key=`lg:{lgId}`,所有资金变动(冻结/解冻/转应收/释放应收)进入时加锁,处理完毕释放,超时时间建议 5s。
- **事务边界**:CmdExe 上 `@Transactional(rollbackFor=Exception.class)`,主表 + 流水表**同一事务**内写入,任何失败整体回滚。
- **重入保护**:分布式锁需支持同一操作人(creator/operator_id)的可重入(避免自身超时释放他人锁)。
- **失败补偿**:Redis 锁获取失败 → 抛出 `BizException("系统繁忙,请稍后重试")`,由调用方决定重试。

### 11.2 性能

- 列表查询必须带分页(`page` 接口)。
- `idx_expiry` 索引覆盖凌晨失效任务扫描;`idx_customer + idx_approval + idx_lg_status` 覆盖选保函查询。
- 单张保函交易明细可能上千条,查询必须 `WHERE lg_id = ?` + `ORDER BY create_time DESC`,避免全表扫描。

### 11.3 凌晨任务

- 凌晨任务(`@XxlJob("letterGuaranteeExpireJob")`)分批处理(每批 100 条),失败单条不影响整体。
- 任务扫描条件:`approval_status=30 AND lg_status=20 AND expiry_date < today`(已审核通过 + 仍有效 + 已到期)
- 任务必须**幂等**:同一保函多次处理结果一致(失效后再次扫描时 `lg_status=30`,自然跳过)。
- 任务执行时间建议 `02:00-05:00`,避开业务高峰。
- 任务与"提前失效"互不冲突:都是 `lg_status: 20→30`,但提前失效是**人工触发**(金融专员主动操作,记录操作人),凌晨任务是**系统自动**(creator=-1, creator_name="system")。
- 凌晨任务**仅对审核通过的保函生效**:草稿/驳回/作废的保函,即便 expiry_date 过期也不处理(这些保函在流程层面已终结,不需要资金失效标记)。
- **必须加 Redis 分布式锁**(多实例部署防重复触发):Job 入口 `redisUtil.tryLock("lg:expireJob", ttlSeconds=3600)`;获取失败 → `log.warn(...)` 跳过本次执行,不抛异常;`finally` 释放锁。**注**:`app-ais-maintain` 项目现有 Job 缺锁是隐患,本模块规避该问题。

### 11.4 多保函分摊

PO 提交时若需要拆分多张保函,业务侧(PO 模块)负责拆分计算,本服务仅按"单张保函一次冻结"语义提供原子操作。**禁止**在保函服务内做"事务拆分多张保函"。

### 11.5 字典维护(偏离 `app-ais-maintain` 决策说明)

`app-ais-maintain` 项目纯走 **client 层 `*StatusEnum` + `IBaseEnum` + `@DictEnumType`** 路线(零 DB 字典表);本设计偏离该风格,**主用 `common_dict` + `common_dict_value` 表 + 国际化 properties 渲染文案**。决策权衡如下:

| 维度 | `app-ais-maintain` 路线(client 枚举) | 本设计(DB 字典 + i18n properties) |
|------|--------------------------------------|-----------------------------------|
| **新增/修改字典项成本** | 改枚举 → 提交 → 发版(依赖业务侧排期) | DBA / 业务管理员后台 SQL 一行(平台字典服务暴露 UI) |
| **业务侧修改权限** | 无(需走研发) | 有(权限点授权金融专员即可) |
| **跨服务一致性** | 各服务各自枚举,易漂移(如 CBU 在 A 服务大写、B 服务小写) | 统一 `dict_type=letter_guarantee_order_type`,PO/SO/保函 多模块共用 |
| **审计追溯** | 跟随代码 git 记录 | 平台 `audit_log` 自动记录(谁改、什么时候改、改了啥) |
| **运行期开销** | 零 DB 查询 | 字典项有 Redis 缓存(平台默认),命中后 ≈ 零开销 |
| **编译期类型安全** | ✅ 强(`switch(approvalStatus)` 漏值编译失败) | ⚠️ 弱(字典值是字符串,运行时校验) |
| **国际化** | 每语言写一份枚举(冗余) | `properties/common_zh_CN.properties` + `common_en_US.properties` 各一份 `dict.*.*=文案`,切换 locale 即可 |

**结论**:保函模块**取 DB 字典 + i18n 路线**,理由:
1. G117 红旗项目明确要求"金融专员可在管理后台维护字典"(业务侧动态调整诉求);
2. 保函的 `approval_status`、`lg_status` 业务规则会演进(如新增"已质押"),DB 字典无需发版即可追加;
3. 与 PO/SO 模块共用订单类型(CBU/SKD/CKD),DB 字典保证跨模块值一致。

**与 `app-ais-maintain` 的共同点**(未偏离):
- 入参校验仍走 client 层枚举 + `@EnumValue`(避免脏值入参);
- 出参翻译仍走 `@DictEnumType`(响应体自动带 i18n 文案);
- 业务判断(`if (status == APPROVED)`)仍引用 client 枚举,不在 Service/Exe 写魔法字符串。

**实施要点**:
- `dict.*.*` keys 已在 `properties/common_zh_CN.properties` 与 `common_en_US.properties` 一一对齐(见 §6.2.1);
- DB 字典初始数据已在 `sql/letter-guarantee-dict.sql` 一次性导入;
- 字典值变更流程:业务侧提交变更 → DBA 评审 → 执行 `INSERT/UPDATE common_dict_value` → 平台 Redis 缓存自动失效刷新;
- **不新增字典表**(平台已有 `common_dict` / `common_dict_value`,本服务零维护)。

### 11.6 历史追溯

- 交易明细表**仅追加,不允许修改/删除**(数据库层面 `UPDATE/DELETE` 权限收紧),确保审计追溯完整。
- 业务上 `delete_status` 永不为 1,但保留字段以符合平台模板。
- MyBatis-Plus 需配置 `@TableLogic` 拦截 `delete_status=0` 条件,避免业务误用 `removeById` 等删除方法。

5. **保函拆分粒度**:PO 提交时按可用金额等比拆分,还是按用户指定比例拆分?边界场景(精度、小数位)如何处理?

7. **保函使用优先级随机性**:平局时随机,具体是按 `RAND()` 在 SQL 层,还是在 Java 层 `Collections.shuffle`?前者性能更优但分页不可控,后者可控但需注意数据量。
8. **应付清单与保函的交互**:转应收后,是否需要同步生成应付清单条目?还是仅记录应收金额,后续由应付模块按规则生成?
9. **历史保函迁移**:系统上线前是否需要将历史保函数据迁移至本服务?若是,数据来源与格式?
10. **审计要求**:除交易明细外,是否需要单独的操作审计日志(谁在何时改了哪些字段)?如需,建议落 `audit_log` 表(由平台提供)。
11. **提前失效的审批层级**:`expireEarly` 是否需要金融管理二次审批?还是金融专员一人即可执行?涉及金额敞口风险时(失效时仍有占用/应收),建议至少金融管理确认。
12. **提前失效的批量能力**:是否需要"批量提前失效"功能(选中多张保函一并失效)?若是,需扩展接口。
13. **审核通过保函的彻底终结**:当前设计提前失效后,`approval_status` 仍为 30(审核通过),仅 `lg_status=30`。是否需要在业务上设置一个终态(如 `lg_status=30` + `approval_status=50`)?若需要,需在凌晨任务/提前失效 中追加 `approval_status` 的同步修改。
14. **Redis 分布式锁 Key 命名规范**:§11.3 凌晨任务用 `lg:expireJob`,新增"批量提前失效"等操作也可能加锁。建议统一定义:
    - 任务类锁:`lg:job:{jobName}`(如 `lg:job:expire`、`lg:job:monthlySettle`);
    - 业务互斥锁:`lg:mutex:{lgCode}`(同一保函同一时刻仅允许一个状态机变更);
    - TTL 默认 60s,Job 类可放宽到 3600s(任务跑完自动释放,`finally` 兜底);
    - 是否需要区分环境(`lg:test:...` / `lg:prod:...`)?同 Nacos 集群共享 Redis 时建议加 env 前缀。
15. **`status_desc` 字段是否冗余**:`export_vehicle_letter_guarantee` 当前保留 `status_desc VARCHAR(256)`,与 `remark`(业务备注)、`approve_remark`(审核意见)语义重叠。三者分工:
    - `status_desc`:平台模板字段,记录通用 `status`(启用/停用)变更原因;
    - `remark`:业务备注,任何用户可填;
    - `approve_remark`:仅审核人填写。
    建议:**保留三字段**(`status_desc` 与平台对齐,改 `status` 时填写),不与业务备注混用;若团队评审认为冗余,可只留 `remark` 并删除 `status_desc`,但需同步调整平台模板。需评审确认。
16. **MyBatis-Plus `autoResultMap=true` 启用范围**:`@TableName(value="...", autoResultMap=true)` 用于需要自定义 `ResultMap`(如枚举映射、JSON 字段、加密字段)的 Entity。本模块需确认:
    - `approval_status` / `lg_status` / `lg_type` / `order_type` / `transaction_type` 是 `VARCHAR` 字段(非枚举),出参翻译走 `@DictEnumType`(基于 properties,不依赖 ResultMap),**无需开启 `autoResultMap`**;
    - 入参 `@EnumValue` 校验由 Jackson 反序列化时拦截,无需 ResultMap;
    - 若后续引入"加密金额"或"JSON 扩展字段",再针对性开启。
    当前决定:**两表 Entity 均不启用 `autoResultMap=true`**,Mapper XML 用平台默认 `BaseResultMap`;若字段类型有调整再行开启,避免无谓的反射开销。
